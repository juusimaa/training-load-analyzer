## Summary

The feature rebuilds features 001–008 as a Python/FastAPI backend and a React/TypeScript client,
next to the untouched .NET reference, and proves it matches.

**Backend.** It ports the domain as pure Python modules:
- `Decimal` for loads;
- `float` for the metrics;
- a formatting module that reproduces .NET's rounding, which is probed and differs from Python's
  own on 5 of 13 values.

It also ports the Strava integration and sync onto `httpx` and stdlib `sqlite3`, and builds the
whole dashboard view server-side, with every displayed string already formatted.

**Frontend.** It renders the Broadsheet page from that view, computes the chart geometry locally
so that switching windows needs no request, and reuses a copy of the reference's stylesheet.

**Parity.** Parity is proved against **golden files generated by the reference itself**, from
shared, purpose-built fixtures, rather than against anyone's reading of it.

## Technical Context

**Language/Version**:
- Python 3.13 (uv-managed);
- TypeScript 5.x (strict) on Node 22+;
- the reference stays on .NET 10.

**Primary Dependencies**:
- backend: FastAPI, Uvicorn, httpx;
- frontend: React 19, React DOM, and Vite as the build tool.

Nothing else at runtime.

**Storage**:
- SQLite via stdlib `sqlite3`;
- the new implementation's own file (`TLA_DATABASE_PATH`), never the reference's (009 FR-022);
- schema versioned with `PRAGMA user_version`.

**Testing**:
- pytest, with `httpx.MockTransport` for Strava and FastAPI `TestClient` in-process;
- Vitest, React Testing Library and jsdom;
- no mocking library in either (Principle IV as amended);
- parity goldens from a .NET generator tool.

**Target Platform**: The developer's machine (macOS). The app is served on `localhost` and used in
modern evergreen browsers.

**Project Type**: A web application: a backend service plus an SPA client.

**Performance Goals**:
- dashboard first content within 2 s for 100+ days, and no slower than the reference (SC-004);
- sync of a current history within 10 s (SC-005).

**Constraints**:
- exactly **one** Uvicorn worker, because the sync guard and status are in-process;
- no request per pointer movement;
- no locale-dependent formatting;
- no credential in any response or log;
- Strava read limits of 100 per 15 minutes and 1,000 per day.

**Scale/Scope**:
- one athlete;
- about 1,200 activities (multi-year);
- one page, plus not-found and error pages;
- about 6 k lines of C# reference to port.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-checked after Phase 1 design: see the end of this
section.*

| Principle / constraint | How the design complies | Status |
| --- | --- | --- |
| **I. Strict TDD** | Tasks will be RED/GREEN/REFACTOR/VERIFY per scenario. The goldens are **expectations**, generated before any Python or TypeScript exists, so every parity test starts red. Hand-computed expectations are ported from the reference's tests, as the first failing tests of each module. | ✅ |
| **II. Domain independence** | `tla/domain/` imports nothing from `tla` or any library beyond stdlib `decimal`/`datetime`/`math`, and names no Strava concept. A test walks its imports. Activity data enters only through the `ActivitySource`-shaped boundary the sync owns. | ✅ |
| **III. Simplicity** | Three runtime backend dependencies and two frontend ones. No ORM, no router, no state library, no chart library, no settings library, no background jobs, no polling. The one added tool, the golden generator, answers SC-001–SC-003 directly. The three copies of the basis-combining rule stay unextracted, as in the reference (004 R12). | ✅ |
| **IV. Testability** | Clock, database path, Strava transport and API client are all inputs. `httpx.MockTransport` is a transport stub, the equivalent of the reference's `StubHttpMessageHandler`, not a mocking library. `unittest.mock`, `vi.fn` and `vi.mock` are not used. | ✅ |
| **V. Isolated integration** | `tla/strava/` (HTTP and shapes) and `tla/sync/` (the only code that knows both Strava and storage) mirror the reference's `Strava/` and `Sync/` split. They are tested at their boundary with recorded responses, separately from domain tests. | ✅ |
| **VI. Deliberate errors** | The dashboard read catches named failure classes into `isUnavailable` and logs them. Sync failures are outcomes, never exceptions. The startup refusal is kept. Standard `logging` only, with no observability stack. | ✅ |
| **VII. Spec adherence** | Every deviation from literal parity is written as a proposed spec amendment, not taken in code (research R1–R4). The recorded `?connect=` gap is kept rather than filled with invented wording. | ✅ (Amendment 1 approved 2026-09-23) |
| **Alt-stack: scope** | All new code is under `alt-stack/`, on a branch from `new_stack`. | ✅ |
| **Alt-stack: backend** | Python/FastAPI; SQLite in its own file; never the reference's store | ✅ |
| **Alt-stack: frontend** | React/TypeScript, lightweight: no UI or chart library | ✅ |
| **Alt-stack: testing** | pytest, with service tests in-process via `TestClient`; frontend tooling chosen here (R12) | ✅ |
| **Alt-stack: independence** | No shared production code or runtime. The stylesheet is **copied**, not referenced. The generator is a test harness that references the reference projects read-only, and nothing in `src/` or `tests/` changes. | ✅ |
| **Alt-stack: merge rule** | Nothing merges into `main` in this feature | ✅ |
| **Strava MCP and test data** | Fixtures are purpose-built and anonymized. Fake tokens are obviously fake (`test-access-…`). | ✅ |

**Structure Decision.** The new implementation lives under `alt-stack/`, next to the reference
rather than replacing any of it, so both build and run side by side (009 FR-003, FR-004). The
backend's packages mirror the reference's projects: `domain` ↔ Domain; `strava`, `persistence`
and `sync` ↔ Infrastructure's `Strava/`, `Persistence/` and `Sync/`; `dashboard` and `api` ↔ Web.
That keeps a one-to-one map for review and for SC-008's comparison. `parity/` sits at the root
because it belongs to neither implementation.

## Phase 2 outline (for `/speckit-tasks`)

These are the dependency order and slices the task list should follow. Each slice starts with its
failing tests.

1. **Parity reference first.** The generator, the fixtures and the committed goldens. Nothing else
   can go red against the reference without them.
2. **US1: domain.** Load → aggregation → metrics → trends → `display`. Hand-computed cases first,
   then the goldens (SC-001), then the independence test.
3. **US2: import.** Mapper → rate limit → client → authorization (with renewal, R10) → store and
   migrations → sync walk (resume, reconcile, outstanding series) → coordinator (SC-003).
4. **US3: dashboard.** `view_builder`/`reader` → `/api/dashboard` → the React page (rail, metric
   row, chart and geometry, recent) → sync interaction (SC-002).
5. **US4: states, devices, appearance.** The remaining states, not-found, error boundary, the
   ported theme tests and the locale runs (SC-006, SC-007).
6. **US5: comparison.** A requirement-to-test map for features 001–008, measurements for SC-008,
   the parity report listing every tolerance and deviation (R1–R4, R17), and the completion
   review against the constitution.
