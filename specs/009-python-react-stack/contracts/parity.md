# Contract: Parity fixtures and golden files

**Feature**: 009-python-react-stack | **Date**: 2026-09-23

These are the shared fixtures 009 FR-022a requires, and the goldens that turn SC-001–SC-003 into
assertions (research R13). Everything here is test data: purpose-built, anonymized and never
copied from a real Strava account (constitution; 005 FR-043).

## 1. Layout

```text
parity/
├── fixtures/
│   ├── histories/<name>.json      # activity sets + "today" + max HR (SC-001, SC-002)
│   ├── sync/<name>/               # a recorded Strava exchange (SC-003)
│   │   ├── scenario.json          # clock, initial store, sequence of HTTP responses
│   │   └── responses/*.json
│   └── probes/display.json        # formatting probe values (research R2)
├── golden/                        # generated by the reference; committed; never hand-edited
│   ├── histories/<name>.json
│   ├── sync/<name>.json
│   └── probes/display.json
└── generator/                     # .NET console tool (references src/…Domain and src/…Web)
```

Regenerate: `dotnet run --project parity/generator`. The tool rewrites `golden/` and nothing
else, so a diff in `golden/` after a reference change is the reviewable signal.

## 2. History fixture

```jsonc
{
  "name": "H3f",
  "today": "2026-09-18",
  "offset": "+03:00",
  "maximumHeartRate": 190,
  "isStravaConnected": true,
  "activities": [
    {
      "id": "fixture-20260918-07",
      "start": "2026-09-18T07:00:00+03:00",
      "movingSeconds": 2700,
      "type": "Cycling",
      "heartRate": [[0, 150], [60, 150]]   // [secondsFromStart, bpm] or null
    }
  ]
}
```

The initial set ports the reference's `Fixtures`: `H1`, `H2`, `H3b`, `ConsecutiveDays(35)`,
`ConsecutiveDays(200)` and `H3f`. It adds these edge fixtures:
- `year-boundary-w53`: activities around 2026-12-28 to 2027-01-04;
- `fractional-offset`: +05:30 and +05:45 starts near midnight;
- `future-dated`: a session dated after today;
- `negative-form`: a heavy block, then rest;
- `display-ties`: loads whose metrics land on `.x5` in 15 significant digits;
- `one-second-hr`: a 3600-sample 1 Hz series, which exercises research R1.

### Surfaces golden (`golden/probes/surfaces.json`)

This covers the surfaces that don't depend on a history, so that 009 SC-002 reaches every surface
008 SC-003 lists. It holds whitespace-normalised text:

- `loading`: `Pages/Dashboard.razor` with a reader that never completes. The rail is compared with
  one substitution, `—` for `0 bpm` (Amendment 1(c)).
- `syncPanel.<row>`: `SyncPanel` for each row of the
  [http-api.md §3](./http-api.md#3-get-apisyncstatus-and-post-apisync) message table.
- `notFound`: `Pages/NotFound.razor`.
- `error`: `Pages/Error.razor` with no request ID. The "Development Mode" block is stripped
  before writing, because it is not ported (Amendment 1(c)).

## 4. Sync fixture and golden

`scenario.json` fixes:
- the clock, in UTC and in the athlete's zone;
- the connection row, with fake tokens. Its `expires_at` is at least the scenario clock + 1 h in
  every scenario except `expired-token`, so the new implementation's renewal (research R10) adds
  no request to the compared sequence;
- the initial activity rows and sync state;
- an ordered list of expected requests (method and URL pattern), each with its canned response:
  status, headers including `X-ReadRateLimit-*`, and a body file.

The initial scenarios are:
- `first-import`: two pages, then an empty page, with 180-day stream fetches;
- `incremental-lookback`;
- `rate-limited-midway`: a 429 on page 2, whose retry time is the next quarter hour;
- `budget-exhausted-on-success`;
- `transient-5xx-then-ok`;
- `unauthorized-401`;
- `reconcile-deletion`;
- `sport-type-changed-to-ebike`;
- `streams-404-manual`;
- `hr-dropouts`: implausible and repeated-time samples;
- `utc-offset-float` (`10800.0`);
- `utc-offset-not-whole-minute` (research R17).

One scenario differs by design: **`expired-token`**. The reference ends it `ReconnectionRequired`
(research R3(1)). The new implementation must renew and complete. Its golden records the
reference's outcome, and the Python test asserts the **specified** behaviour instead, with a
comment naming Amendment 1(b). It is the only golden a test deliberately does not match.

The golden records:
- the final activity rows, as domain values (id, start with offset, moving time, type,
  heart-rate samples, outstanding flag);
- the sync state (resume point, last outcome);
- the `SyncResult` (counts, skipped with reasons, removed ids, discarded counts, outcome,
  retry-after);
- the `SyncMessage` text;
- the sequence of requests actually issued.

## 5. Tolerances

These are the only allowed differences between the goldens and the new implementation.

| Quantity | Comparison | Source |
| --- | --- | --- |
| Loads, daily/weekly points, trend changes | \|a − b\| ≤ 1e-20 | research R1, Amendment 1(a) |
| Fitness, Fatigue, Form | \|a − b\| ≤ 1e-4 (003 FR-029); in practice equal to 1 ulp | 003 |
| Every string in `view` and `renderedText` | exact | 009 SC-002 |
| SVG coordinates, bar and slot numbers | parsed, element-wise \|a − b\| ≤ 0.01 | research R8 |
| Tick labels, slot counts, bar counts, `null`-ness | exact | 008 FR-006 |
| Sync outputs | exact, except `expired-token` (above) | 009 SC-003 |
